# 검증된 변경만 커밋·푸시하기 (gated commit & push)

이 스킬의 단 하나의 불변 규칙: **리뷰와 검증을 통과하지 않은 변경은 GitHub에 올리지 않는다.**
아래 게이트를 순서대로 통과할 때만 커밋·푸시가 일어난다. 어느 게이트든 실패하면 즉시 멈추고, 무엇이
왜 막혔는지 알린 뒤 커밋/푸시를 하지 않는다. "일단 올리고 나중에 고치자"는 이 스킬에 존재하지 않는다.

## 게이트 1 — 리뷰 수행 확인 (필수)

이 게이트가 요구하는 것은 리뷰가 **수행·판단되었는가**이지, 리뷰 지적이 **반영되었는가**가 아니다.

- 이번 세션에서 현재 변경을 대상으로 `review-and-apply`가 이미 돌아 리뷰·판단까지 끝났다면 통과.
- 그렇지 않다면(리뷰를 안 했거나, 리뷰 이후 코드를 또 바꿨다면) **먼저 `review-and-apply` 스킬을
  실행**한다(Skill 도구로 `review-and-apply` 호출). 리뷰·판단이 끝난 뒤에 다음 게이트로 간다.
- **아무것도 반영하지 않은 리뷰도 통과다.** Claude가 코드와 대조해 리뷰 지적을 전부 거짓 양성·규약
  충돌·범위 밖으로 판단해 굳이 고치지 않기로 했다면, 그것도 정당한 리뷰 결과다. 이 경우 코드는 그대로
  두고 커밋·푸시로 진행한다. 핵심은 "검토가 이뤄졌다"는 것이지 "수정이 있었다"가 아니다.
- 다만 리뷰 과정에서 **사용자에게 물어볼 판단 보류 항목**이 남아 있으면, 그게 정리되기 전에는
  푸시하지 않는다(반영/미반영을 아직 못 정한 상태이므로).

## 게이트 2 — 검증 통과 (필수)

반영된 최종 트리가 실제로 빌드/린트를 통과하는지 객관적으로 확인한다:

```bash
bun run check && bun run build
```

- `check`(Biome 린트/포맷)와 `build`(`tsc -b` + 프로덕션 빌드)가 **둘 다 통과**해야 한다.
- `check`가 포맷 문제로 실패하면 `bun run check:fix`로 고친 뒤 다시 `check && build`를 돌린다(수정이
  생기면 그 자체가 새 변경이므로 게이트 1의 "리뷰 이후 코드 변경" 여부를 재확인).
- 하나라도 실패하면 **커밋/푸시하지 않는다.** 원인을 고치고 이 게이트를 다시 통과시킨다.

## 게이트 3 — 시크릿 안전 확인 (필수)

민감 파일이 커밋에 섞이지 않는지 확인한다. `.env`(GITHUB_PAT)와 `.mcp.json`(API 키)은 gitignore
대상이지만, 스테이징 전후로 한 번 더 확인한다:

```bash
git status --short --untracked-files=all
git ls-files --error-unmatch .env .mcp.json 2>/dev/null && echo "위험: 시크릿이 추적되고 있음"
```

- 스테이징 목록에 `.env`, `.mcp.json`, 키·토큰류 파일이 보이면 **중단**하고 사용자에게 알린다. 이런
  파일을 추적 파일로 옮기거나 커밋하지 않는다.

## 커밋 & 푸시

세 게이트를 모두 통과했을 때만 진행한다.

1. **스테이징** — 의도한 변경만 담는다. 보통 `git add -A`면 되지만(gitignore가 시크릿을 걸러줌),
   `git status`로 담긴 목록을 눈으로 확인한다.
2. **커밋** — 변경 내용을 간결하게 요약한 메시지. 무엇을 왜 바꿨는지 한 줄 제목 + 필요시 본문.
   커밋 메시지 끝에는 아래 한 줄을 반드시 포함한다:

   ```
   Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>
   ```

   힌트: heredoc으로 여러 줄 메시지를 안전하게 전달한다.
   ```bash
   git commit -m "$(cat <<'EOF'
   <제목: 한 줄 요약>

   <본문: 필요 시 무엇을/왜>

   Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>
   EOF
   )"
   ```
3. **푸시** — 현재 브랜치를 origin에 푸시한다:
   ```bash
   git push origin HEAD
   ```
   - 원격이 없으면(`git remote -v`가 비어 있음): 푸시하지 않고 원격 설정을 안내한다.
   - 인증 실패 시: 커밋은 로컬에 남은 상태이므로, 원인(자격 증명/원격 URL)을 알리고 푸시만 재시도하게
     안내한다. gh CLI가 없으면 `git push` 자격 증명 설정을 안내한다.
4. **보고** — 커밋 해시, 푸시된 브랜치/원격, 그리고 통과한 게이트(리뷰 완료 / check·build 통과)를
   요약해 알린다. 원격에 반영된 커밋 URL이 있으면 함께.

## PROGRESS.md 갱신

푸시가 끝나면 `docs/PROGRESS.md`의 "마지막 검증"·"최근 작업"을 이번 반영 기준으로 갱신한다
(프로젝트 규약).

## 브랜치 참고

기본적으로 현재 브랜치(현재 `main`)를 그대로 푸시한다 — 개인 포트폴리오 저장소라 main 직접 푸시가
자연스럽다. 만약 PR 흐름을 원하거나 보호된 브랜치라면, 사용자에게 확인 후 새 브랜치를 만들어
푸시하고 PR을 여는 방식으로 전환한다.
