# 포트폴리오 · 이력서 내용 리뷰 받고 반영하기

구조는 셋이다. **리뷰어(읽기 전용 서브에이전트)** 가 비판하고 수정안을 낸다 → **메인 Claude** 가 원문 ·
원 저장소 · 확인된 사실과 대조해 판단한다 → 통과한 것만 메인 Claude가 고친다. 리뷰어는 파일을
고치지 않는다. 편집을 한 곳에 모아야 사이트 · 이력서 · 안내자 지식이 서로 어긋나지 않는다.

리뷰어는 일부러 가혹하게 굴리지만, **리뷰어의 확신은 근거가 아니다.** 원 저장소 이력과 사용자가 확인해 준
사실이 진실의 원천이다.

## 1. 범위 정하기

사용자 말에서 범위를 정한다. 말이 없으면 **최근 변경분**으로 한다.

| 범위 | 대상 |
|---|---|
| 최근 변경분 | `git diff HEAD --name-only`에 걸린 콘텐츠 파일의 바뀐 부분 |
| 프로젝트 하나 | `src/data/projects.ts`의 그 프로젝트 블록 + `resume/resume.md`의 해당 절 + `resume/content.js`의 해당 항목 |
| 사이트 전체 | `src/data/*.ts` 전부 |
| 이력서 | `resume/content.js`(PDF) · `resume/resume.md`(긴 원고) |
| 전체 | 위 전부 |

콘텐츠 파일: `src/data/profile.ts` · `experience.ts` · `activities.ts` · `skills.ts` · `projects.ts`,
`resume/content.js` · `resume/resume.md` · `resume/evaluation.md`.

원 저장소(사실 대조용, 모두 읽기만): SafeOps `~/Desktop/safeops`, 침례교 `~/Desktop/baptism_app`(`docs/troubleshooting.md`),
아이머그 `~/Desktop/imug`, Plus SMS `~/Desktop/sms`. 아이머그 · 침례교 · SMS는 공동 저장소라 **본인 커밋만** 근거가 된다
(`docs/PROGRESS.md`의 32~33차 항목에 작성자 목록이 있다).

## 2. 리뷰어 호출 — 두 렌즈를 병렬로

`reviewer-brief.md`를 읽어 두 개의 서브에이전트(`general-purpose`)를 **한 메시지에서 동시에** 띄운다.
각 프롬프트에는 브리프 전문 + 렌즈 이름 + 범위(파일 · 줄 범위) + 원 저장소 경로를 넣는다.

- **렌즈 A — 채용 담당자 · 시니어 면접관**: 30초 안에 무엇이 읽히나, 과장 · 모호함 · 번역투 · 중복 · 구성,
  "그래서 당신이 한 게 뭔데?"에 답이 되는가, 면접에서 공격받을 문장.
- **렌즈 B — 사실 검증관**: 모든 주장 · 수치 · 날짜 · 역할 · 코드 발췌를 원 저장소(git log · blame · show)와 대조.
  본인 커밋인가, 발췌가 원문 그대로인가, 전/후가 실제로 동작이 달랐나.

범위가 작으면(사례 두세 개) 렌즈 하나로 합쳐 한 에이전트만 띄워도 된다.

## 3. 판단 게이트 (핵심)

지적마다 **직접 확인**한다 — 해당 파일 · 줄을 읽고, 사실 문제면 원 저장소에서 `git show` · `git blame`으로 본다.
판단 기준은 `CLAUDE.md`, `docs/PROGRESS.md`(특히 "확인된 사실" · 결정사항 · 함정 노트), 어조 규칙이다.

- **반영**: ① 지적이 사실이다 ② 읽는 사람에게 실제로 손해다(틀림 · 과장 · 오해 · 읽기 어려움) ③ 수정안이
  사실에 맞고 규약과 충돌하지 않는다. 수정안이 어색하면 뜻만 살려 메인 Claude가 다시 쓴다.
- **미반영**: 원문 대조 결과 틀린 지적 / 취향 차이 / 프로젝트 결정과 충돌(예: 사이트는 말하듯, 이력서는 평이하게 —
  두 문체를 하나로 맞추라는 제안) / **사용자가 이미 확인해 준 사실**을 저장소에 없다는 이유로 빼라는 제안.
- **사용자 확인**: 저장소로 판정할 수 없는 사실(재직 기간 · 팀 구성 · 저장소 밖 측정 · 출시 상태 · 누가 방향을
  정했는가)이나, 사례를 통째로 빼거나 주어를 바꾸는 큰 결정. `AskUserQuestion`으로 한 번에 묶어 묻는다.
  답은 `docs/PROGRESS.md`의 "확인된 사실"에 적어 다음 리뷰가 같은 걸 다시 묻지 않게 한다.

**지어내지 않는다.** 리뷰어가 "수치를 넣으면 설득력이 산다"고 해도 근거 없는 수치는 넣지 않는다.
검증이 안 된 것은 "정적 검증만" · "미확인"처럼 있는 그대로 적는 쪽이 낫다.

## 4. 반영 & 검증

- 같은 내용이 세 곳에 있다: 사이트(`src/data`) · PDF 원고(`resume/content.js`) · 긴 원고(`resume/resume.md`).
  하나를 고치면 나머지도 같은 사실로 맞춘다(문체는 각자의 것으로).
- 어조: 사이트는 개발 중심으로 말하듯, 이력서는 비유 없이 평이하게. `docs/PROGRESS.md` §3 "본문 용어는 풀어 쓴다"
  목록으로 한 번 훑는다.
- 순서: `bun run knowledge` → `bun run check:fix` → 새 한글이 들어갔으면 `python3 scripts/subset-fonts.py`
  (요구 패키지가 없으면 스크래치패드 venv) → `bun run build`.
- `content.js`를 고쳤으면 PDF를 뽑아 쪽 경계와 마지막 쪽을 본다. 정해진 쪽수는 없다 — 쪽수를 맞추려고 내용을
  빼지 말고, 항목마다 최대한 간략하게 쓴다(`resume/README.md` 편집 원칙).

## 5. 보고

`docs/PROGRESS.md`의 현재 상태 · 확인된 사실 · 함정을 갱신하고(이력 나열 금지), 지적별 처리를 표로 보고한다.

```
| # | 렌즈 | 위치 | 지적 요지 | 판단 | 처리 |
|---|------|------|-----------|------|------|
| A3 | 면접관 | projects.ts:812 | 결과가 수치 없이 형용사뿐 | 타당 | 반영 — 실측 수치로 교체 |
| B1 | 사실 | resume.md:470 | 저장소에 측정 흔적 없음 | 확인된 사실 | 미반영 — 사용자 확인(저장소 밖 측정) |
| A7 | 면접관 | content.js:88 | 사이트 문체로 통일 제안 | 규약 충돌 | 미반영 — 이력서는 평이한 문체 |
```

사용자에게 불편한 지적(본인 작업이 아님 · 과장)이라도 사실이면 그대로 보고한다. 커밋은 하지 않는다 —
사용자가 원하면 `commit-push`로 넘긴다.
