# 리뷰 받고 타당하면 반영하기 (Codex review → judge → apply)

방금 끝낸 변경을 Codex에게 리뷰받되, **리뷰 결과를 그대로 반영하지 않는다.** Codex(및 모든 자동
리뷰어)는 실제 버그와 함께 거짓 양성(false positive), 이 프로젝트의 규약과 충돌하는 스타일 취향,
범위 밖 제안을 섞어 낸다. 이 스킬의 가치는 그 사이에 **Claude의 판단 게이트**를 두는 것 — 코드와
대조해 실제로 맞는 지적만 골라 반영하고, 나머지는 이유와 함께 남긴다.

## 언제 이걸 쓰나

- 기능/리팩터링/버그 수정 등 **하나의 작업 단위가 끝났을 때** 마무리 검토로.
- 사용자가 리뷰 후 수정까지 원할 때. 리뷰 결과만 보고 싶다면 `/codex:review`를 안내하고 멈춘다.

## 워크플로우

### 1. 리뷰할 변경이 있는지 확인

Codex 리뷰는 로컬 git 상태를 대상으로 한다. 먼저 변경 유무를 본다:

```bash
git rev-parse --is-inside-work-tree 2>/dev/null && git status --short --untracked-files=all
```

- git 저장소가 아니면: 리뷰 대상이 없다고 알리고, 필요하면 `git init` 후 다시 시도하도록 안내.
- 변경이 전혀 없으면(추적/미추적 모두 비어 있음): 리뷰할 게 없다고 알리고 멈춘다.
- 추적되지 않은 새 파일도 리뷰 대상이다 — `git diff`가 비어 있어도 `git status`에 파일이 있으면 진행.

### 2. Codex 리뷰 실행

Codex 플러그인의 companion 스크립트를 직접 호출한다(슬래시 커맨드 `/codex:review`는 모델이 직접
호출할 수 없으므로 스크립트를 쓴다). 버전 디렉토리는 바뀔 수 있으니 최신 경로를 글롭으로 해석한다:

```bash
CODEX_SCRIPT="$(ls -t ~/.claude/plugins/cache/openai-codex/codex/*/scripts/codex-companion.mjs 2>/dev/null | head -1)"
node "$CODEX_SCRIPT" review --wait
```

- `--wait`로 **포그라운드 실행** — 결과를 받아 같은 흐름에서 판단·반영해야 하기 때문. (변경이 아주
  크면 시간이 걸릴 수 있음을 사용자에게 알린다.)
- 스크립트가 인증/설정 오류를 내면(예: Codex 미설정): 사용자에게 `/codex:setup`을 한 번 실행하도록
  안내하고 멈춘다. 이 스킬은 설정을 대신 하지 않는다.
- 스크립트 stdout(리뷰 원문)을 확보한다. 사용자에게 원문 요지를 간단히 보여줘도 좋다.

설계·접근 자체를 도전적으로 검토받고 싶다는 신호가 있으면 `review` 대신 `adversarial-review`를 쓴다.

### 3. 각 지적을 판단한다 (핵심 단계)

리뷰에서 나온 지적을 하나씩, **코드와 직접 대조하며** 타당성을 평가한다. 반영 기준:

**반영한다** — 다음을 모두 만족할 때:
- 지적이 **사실**이다. 해당 파일·라인을 실제로 읽어 확인했고, 주장한 문제가 코드에 존재한다.
- 이 코드베이스에서 **실제 결함이거나 분명한 개선**이다(버그, 잘못된 로직, 접근성/성능 문제, 취약점,
  명백한 가독성 저해 등).
- 수정이 **안전하고 범위 안**이다 — 방금 한 작업과 관련되고, 무관한 대규모 변경을 부르지 않는다.

**반영하지 않는다(이유를 남긴다)** — 다음 중 하나라도 해당할 때:
- 코드와 대조했더니 **틀린 지적**(거짓 양성)이다.
- 이 프로젝트의 **의도된 규약과 충돌**한다. 예:
  - Biome 설정과 어긋나는 포맷/스타일 취향(4칸 들여쓰기, `import type` 분리 등은 이미 규약).
  - 의도적으로 둔 `biome-ignore` 주석이나 CSS의 `!important`(Lenis·reduced-motion용)를 문제 삼는 것.
  - "데이터는 `src/data/*.ts`로 분리" 같은 아키텍처 결정을 되돌리라는 제안.
- **범위를 크게 벗어나는** 리팩터링/재설계 제안(작업 마무리 검토의 목적과 안 맞음). → 반영하지 말고
  "후속 제안"으로 따로 기록만.
- 판단이 애매하면 반영하지 말고 **사용자에게 물어본다.** 확신 없는 자동 반영이 이 게이트의 취지에
  가장 어긋난다.

CLAUDE.md와 `docs/PROGRESS.md`의 규약·결정사항을 판단 기준으로 함께 참고한다.

### 4. 타당한 것만 반영

- 판단을 통과한 지적만 Edit/Write로 반영한다.
- 각 수정은 최소 침습적으로, 주변 코드 스타일에 맞춰서.

### 5. 검증

프로젝트 규약대로 반영 결과를 검증한다(변경이 없었으면 생략):

```bash
bun run check:fix && bun run build
```

- `check`(Biome)와 `build`(`tsc -b` + 프로덕션 빌드)가 모두 통과해야 마무리. 실패하면 원인을 고치고
  다시 검증한다.

### 6. PROGRESS.md 갱신 & 보고

- `docs/PROGRESS.md`의 관련 섹션(최근 작업·마지막 검증 등)을 갱신한다(프로젝트 규약).
- 사용자에게 **판단 요약표**로 보고한다 — 지적별로 무엇을 어떻게 처리했는지 투명하게:

```
| 지적 | 판단 | 처리 |
|------|------|------|
| <리뷰 지적 요지> | 타당 | 반영 (파일:라인, 무엇을 바꿨는지) |
| <리뷰 지적 요지> | 거짓 양성 | 미반영 — <코드와 대조한 근거> |
| <리뷰 지적 요지> | 규약 충돌 | 미반영 — <어떤 규약과 왜> |
| <리뷰 지적 요지> | 범위 밖 | 후속 제안으로 기록 |
```

- 반영이 있었다면 검증 결과(check/build 통과 여부)를 함께 알린다.
- 원하면 반영 후 다시 한 번 리뷰를 돌려(2번 반복) 잔여 이슈를 확인할 수 있음을 제안한다.

## 원칙

리뷰어의 권위에 눌리지 말고, **코드가 진실의 원천**이다. 지적이 그럴듯해도 코드로 확인되지 않으면
반영하지 않는다. 반대로, 사용자에게 불편한 지적이라도 사실이면 솔직하게 반영·보고한다. 이 스킬은
"리뷰를 따르는" 것이 아니라 "리뷰를 검증해 옳은 것만 취하는" 것이다.
