## 3. 핵심 역량

### 3-1. 웹과 앱을 모두 개발합니다

- React 웹(Vite · Next.js)과 React Native 앱(Expo managed · **Expo bare**)을 모두 실제 서비스로 출시했습니다.
- 웹 페이지가 앱의 WebView 안에서 동작하는 서비스에서 앱의 정지 명령을 웹이 한 곳에서 받는 **브릿지 수신부**를 만들었습니다(아이머그).
- iOS · Android 네이티브 폴더를 직접 관리하는 Expo bare 프로젝트에서 Android 정책 변경(targetSdk 36)에 대응했습니다(침례교 전용앱).

### 3-2. 라이브러리로 해결되지 않으면 네이티브까지 직접 다룹니다

- 알림 라이브러리로 무음 모드를 우회할 수 없어 **Kotlin으로 Expo 네이티브 모듈**을 만들어 긴급 알림 채널을 직접 생성했습니다(SafeOps).
- 긴급 알림 여부를 앱이 추측하지 않고 **서버가 보내는 데이터로 판단**하도록 앱과 서버의 역할을 나눴습니다(SafeOps).
- edge-to-edge 전환으로 틀어진 상단 여백을 **SDK 35 기준값 하나**로 네이티브와 JS가 함께 쓰도록 정리했습니다(침례교 전용앱).

### 3-3. 인증과 상태 관리를 안정적으로 설계합니다

- 여러 요청이 동시에 만료돼도 **토큰 갱신은 한 번만** 일어나도록 했습니다(침례교).
- 토큰이 만료되기 전에 **미리 갱신**합니다: 만료 5분 전(침례교 · Plus SMS).
- 여러 사람이 한 기기를 쓰는 앱에서 **로그아웃 시 토큰 · 캐시 · 위치 정보를 한 번에 초기화**했습니다(SafeOps).
- 서버 데이터는 TanStack Query, 로그인 세션과 전역 모달은 Context, 나머지는 각 화면에서 관리하도록 나눕니다.
- 같은 값을 화면마다 따로 계산하다 결과가 어긋난 문제를 **계산 함수 하나로 통합**해 해결했습니다(SafeOps).

### 3-4. 측정하고, 실제 기기로 검증하고, 문서로 남깁니다

- 성능은 재서 확인합니다: 가상화 전후 10,000건 렌더링 **1,300.9ms → 32.6ms**(Plus SMS).
- 기준값은 실측으로 정합니다: 실내 네트워크 측위 갱신 간격 **7~185초**를 측정해 필터 기준(10분 · 5초)을 정했습니다(SafeOps).
- 실제 기기에서 확인합니다: 무음 상태에서 앱 실행 중 · 백그라운드 · 종료 세 가지 경우를 양 플랫폼에서 확인했습니다(SafeOps).
  NFC 출석도 앱 첫 실행 · 백그라운드 복귀 · 연속 태그 · 비로그인 상태를 실제 기기에서 확인했습니다(침례교).
- 테스트로 품질을 관리합니다: **테스트 1,050개(88 suites)**, 테마 글자 대비 기준도 테스트로 검증합니다(SafeOps).
- 순서를 바꾸면 조용히 기능이 깨지는 부분(Provider 순서 등)을 문서로 남깁니다(침례교).

## 5. 프로젝트 상세

각 프로젝트는 **개요 → 배경 → 문제 · 해결 · 결과** 순서입니다. 면접에서 "가장 어려웠던 문제"를 물으면
각 프로젝트의 첫 번째 사례부터 이야기하면 됩니다.

### 5-1. SafeOps · 행사 현장 경비 근무 앱

- **소속** 센티언트 시스템즈 플랫폼 엔지니어링 팀
- **기간** 2026.07 ~ 현재 · **역할** 앱 개발 1인(설계 · 개발) · **팀** 앱 1명 · 백엔드 1명 · **플랫폼** iOS · Android
- **성과** App Store · Google Play 출시(현재 1.0.2) · 라이트/다크 테마 · 테스트 1,050개(88 suites)
- **기술** React Native, Expo, TypeScript, TanStack Query, React Navigation, FCM · Notifee,
  Expo Modules(Kotlin), 네이버 지도 SDK, EAS Update

**배경.** 경비 인력은 근무 중 무전기를 들고 이동하고, 휴대폰은 주머니에 넣어 둡니다. 사용자가 앱을 열어야
동작하는 일반적인 앱과 달리, **앱을 열지 않아도 동작해야** 했습니다. 계정은 관제실이 발급하고 근무가 끝나면
닫으며, 야간 근무가 많아 테마도 두 가지가 필요했습니다.

**① 무음 모드에서도 울리는 긴급 알림**

- 문제: 긴급 지시는 벨소리를 꺼 둬도 울려야 합니다. 알림 채널을 나눠 방해 금지 모드는 통과했지만 무음 모드는
  통과하지 못했습니다. 무음 모드에서는 알림 소리가 꺼지기 때문에 알람 소리로 보내야 하는데, 사용하던 알림
  라이브러리에는 이 설정을 넣을 방법이 없었습니다.
- 해결: 긴급 알림 채널만 Kotlin으로 만든 Expo 네이티브 모듈에서 알람 용도로 직접 생성했습니다. Android 알림 채널은
  한 번 만들면 소리 설정을 바꿀 수 없어 채널 ID를 새로 만들었습니다. 삼성 기기는 벨소리 모드에서 한 번 더 막아서,
  무음 · 진동 모드일 때만 앱이 직접 알람 소리와 진동을 냅니다. 긴급 여부는 앱이 아니라 **서버가 보내는 데이터**로
  판단합니다.
- 전 → 후 (5f6e368): `notifee.createChannel({ id: "dispatch_critical", bypassDnd: true })` +
  `isCritical = data.type === "FIELD_RESPONSE"` → 네이티브 `ensureCriticalChannel("dispatch_critical_alarm")`
  (USAGE_ALARM) + 서버가 보낸 채널(Android) · critical 사운드(iOS)로 판단. 전에는 서버가 일반으로 보낸 대응 요청도
  앱이 켜져 있을 때만 긴급으로 울렸습니다.
- 전 → 후 (b9c3184): 채널 상태를 `boolean | null`로 돌려줘 "채널 없음"과 "확인 전"이 둘 다 `null`이던 것 →
  `"bypassing" | "blocked" | "unavailable"`로 나눠 `unavailable`이면 재시도 배너를 띄웁니다.
- 결과: Android · iOS 실기기에서 무음 상태의 앱 실행 중 · 백그라운드 · 종료 세 가지 경우를 모두 확인했습니다.
  채널 생성에 실패하면 홈 화면에 다시 시도 안내를 띄웁니다. (벨소리 모드 대응은 삼성 기기에서 발견했지만, 규칙
  자체는 모든 Android 기기에 똑같이 적용됩니다.)

**② 다음 요원이 앞사람의 화면도, 자격도 물려받지 않게 (658fcb3 · 1fae958 · d5e4558)**

- 화면: 교대 근무로 한 기기를 여러 사람이 쓰는데, 로그아웃 후 다음 사람이 로그인하면 이전 사람의 데이터가 보일 수
  있었습니다. 처음 로그아웃은 토큰만 지웠고(`clearAccessToken()`), 응답 인터셉터는 401을 에러로 바꿔 던지기만
  해서 화면은 로그인된 채 요청이 계속 실패했습니다. 로그아웃하거나 쓰는 도중 401(세션 만료 코드 포함)을 받으면
  토큰 · 쿼리 캐시 · 위치 정보를 한 번에 초기화하도록 바꿨습니다(658fcb3). 403은 권한 에러로 두고, 부팅 때 세션
  복원이 4xx로 실패하면 그때 세션을 폐기합니다.
- 좌표: OS 백그라운드 작업은 앱이 죽어도 남아, 강제 종료 후 다시 열면 로그인 3초 전에 좌표가 올라갔습니다(실기기
  재현). 교대 구간이면 다음 요원 기기에서 앞 요원 자격으로 전송됩니다. 라이브러리를 바꾼 뒤에는 늦게 끝나는 정지
  사이에 도착한 네이티브 이벤트가 다음 근무 구독자에게 갈 수 있었습니다.
- 전 → 후: `if (AppState.currentState === "active") return;` → 메모리에만 두는 `hasTakenOverShift` 게이트,
  정지 요청 시 큐에 넣기 전에 게이트를 닫고 세대 번호를 올림(Codex 리뷰 지적 반영). 라이브러리 교체 뒤에는
  `emit`의 첫 관문 `if (!isSessionOpen || subscribers.size === 0) return false;`.
- 결과: Android 백그라운드 75초에 작업 진입 14회 · iOS 60초에 53회를 전부 차단(전송 0), 왕복 · 토글 · 재로그인
  전 구간 중복 0건.

**③ 위치 전송 상태를 정확하게 표시**

- 문제: 처음 상태 판정은 연속 전송 실패 횟수만 봤습니다. 그런데 GPS 측정에 실패하면 보낼 좌표가 없어서
  실패도 쌓이지 않았고, 관제실은 위치를 받지 못하는데 화면은 계속 정상(ONLINE)이었습니다. 또 홈과 설정 화면이
  같은 상태 표시를 따로 계산했는데, 설정 쪽 계산은 근무 종료를 보지 않아 근무가 끝난 뒤에도 경고가 남았습니다.
- 해결: 판정에 "관제실이 마지막으로 위치를 받은 뒤 흐른 시간"을 더했습니다(첫 좌표 전 90초, 이후 3분).
  근무가 끝나면 전송과 GPS를 함께 멈추고, 두 화면의 계산은 근무 종료까지 보는 함수 하나로 합쳤습니다.
- 전 → 후 (`locationStore.tsx`, 7b05961):
  `consecutiveFailures < STALE_AFTER_FAILURES` 만 보던 판정 → 같은 조건 `&& !isSilent`
  (`isSilent` = 마지막 성공 전송 뒤 `STALE_AFTER_SILENCE_MS`(3분) 경과)
- 전 → 후 (7b7a2e5): 설정 화면 안의 `isTimerRunning = permission === "granted" && isTransmitting` →
  `utils/transmissionStatus.ts`의 `resolveTransmissionStatus()`가 `isOffDuty`면 중립색 `OFF DUTY`를 돌려주고,
  홈과 설정이 이 함수 하나를 부릅니다.
- 위치 필터: 10초마다 측정한 좌표에서 10분 넘은 좌표, 이전 위치로 튄 좌표(3회 연속일 때만 인정), 중복 좌표(5초가
  지나면 다시 전송)를 걸러 냅니다. 오래된 좌표 기준은 처음에 90초였는데, 실내에서 네트워크 측위 갱신 간격을 측정해 보니
  7~185초로 들쭉날쭉해 전부 걸러지는 문제가 있어 10분으로 늘렸습니다(`MAX_LOCATION_AGE_MS = 90_000` →
  `10 * 60_000`, 56cb901). 역전도 "한 번이라도 뒤로 가면 버림"에서 "연속 3회 + 측정 시각이 앞으로 갈 때만 인정"으로
  바꿨습니다. 모든 좌표가 걸러져도 10초마다 마지막 좌표를 다시 보냅니다.
- 전 → 후 (2436c36): GPS 소스를 다시 열지도 같은 `isSilent`(서버가 받아 준 시각 기준)로 판단해, API 장애가 3분
  이어지면 멀쩡한 GPS를 30초마다 껐다 켰습니다 → 좌표가 도착한 시각(`lastCoordinateAtRef`)으로 따로 잰
  `isSourceSilent`로만 재시작합니다. 관제실에 들어가는지와 GPS가 도는지는 다른 질문이라 시각도 따로 둡니다.
- 정지 감지: 처음엔 `disableStopDetection`을 잘못된 설정 그룹에 넣어 라이브러리가 무시했고(타입 검사는 통과),
  기본값대로 5분 뒤 GPS가 꺼졌습니다. 실기기에서 4.5분 만에 좌표가 멎는 것을 로그로 확인하고 고쳤습니다(3b864de).
- 결과: 위치 전송이 끊기면 홈 화면에 바로 표시되고, 근무가 끝나면 홈과 설정 화면이 동시에 근무 종료로 바뀝니다.
  (전송 주기 10초 · 전송 중단 감지 3분)

**④ 좁은 구역을 도는 요원이 제자리로 읽히던 문제 (456a06d · 3b864de)**

- 문제: 5분 순회 실측에서 Android 좌표가 14건, 최대 공백 63.9초. 원인은 네 겹이었습니다 — 이동 주기가 거리(5m)

  시간(90초)보다 짧아 재시작 루프, 시계 롤백에 약한 역전 필터.
- 전 → 후: `distanceFilter: MOVING_DISTANCE_FILTER_M(5)` → `distanceFilter: 0` + `locationUpdateInterval`·
  `fastestLocationUpdateInterval` 5초, `onMotionChange`에서 `emit(event.location)`, 대기 시한 60초 → 2분.
- 결과: 같은 5분 순회에서 14건 · 중앙값 7.7초 · 최대 63.9초 → 58건 · 5.0초 · 최대 10.0초. 이후 3b864de에서 정지
  감지를 끄고(`activity.disableStopDetection`) 같은 좌표도 받게(`allowIdenticalLocations: true`) 해 10초 고정
  주기로 바꿨습니다.

**⑤ 빈 catch가 Android 포그라운드 알림을 지운 문제 (583184c)**

- 문제: 알림을 expo-notifications에서 Firebase Messaging + Notifee로 옮긴 뒤, Android 포그라운드에서 지시 알림이
  뜨지 않았습니다. Notifee는 진동 패턴에 0이 있으면 채널 생성을 거부하는데(`[0, 250, 150, 400]`), 그 실패를
  `ensureDispatchChannel().catch(() => {})`가 삼켰습니다. 백그라운드는 OS 기본 채널로 폴백해 멀쩡해 보였습니다.
- 전 → 후: 패턴 `[0, …]` → `[1, …]`, 앱 시작부의 빈 catch 제거, 채널 생성을 try/catch로 감싸 실패를 기록,
  `sound: "default"` 명시(비우면 무음 채널). 채널 생성 거부 경우를 테스트로 추가.

**⑥ Android에서만 좌표가 한 번도 오지 않던 문제 (dd97cd4)**

- 문제: `expo-location`과 위치 라이브러리가 같은 백그라운드 권한을 동시에 요청했습니다. Android 11+는 이 권한을
  앱 다이얼로그로 받을 수 없어 `expo-location`이 설정 화면을 여는데, 그 전환이 위치 라이브러리의 권한 안내를 끊어
  `ready()`가 끝나지 못했고 추적이 시작되지 않았습니다. 권한 안내는 라이브러리 기본 영문(`[CHANGEME] ...`)이었습니다.
- 전 → 후: `requestBackgroundPermissionsAsync`로 직접 요청 → Android에서는 `getBackgroundPermissionsAsync`로
  읽기만 하고 요청은 추적을 켜는 쪽에 맡김(테스트 2건으로 고정). 안내 문구는 한국어로.
- 결과: Note20 실기기에서 권한 허용 10초 뒤 첫 좌표, 정확도 ±9.5m.

**⑦ 라이트 · 다크 테마**

- 문제: 스타일 코드가 색상 값을 직접 참조하고 있어 테마를 바꿀 수 없는 구조였습니다.
- 해결: 모든 스타일을 색상 팔레트를 받아 만들어지는 구조로 바꿨습니다(2e96ca2, 스타일 파일 36개 · 104파일
  +1504/−582). 전에는 `StyleSheet.create({ base: { backgroundColor: colors.surface } })`처럼 모듈을 읽는 순간 색이
  굳었고, 지금은 `createStyles((colors) => ({ ... }))`가 테마마다 한 번 만들어 캐시합니다. 두 테마는 같은 색상
  이름을 쓰고, 상태 색은 색감은 유지하면서 밝기만 바꿨습니다. 다크 한 벌만 보던 대비 테스트를 두 팔레트 모두로
  넓혔고, 일반 글자는 AA 4.5:1, 색 배경 위 글자는 큰 글자 기준 3:1로 검증합니다.
  시스템 테마 연동은 네이티브를 다시 빌드해야 해서 이미 배포된 앱에는 적용할 수 없기 때문에, 설정 화면에서 고르는
  방식으로 만들어 **EAS Update(OTA)** 로 배포했습니다.
- 결과: 테마를 바꾸면 지도까지 야간 색상으로 함께 바뀝니다.

**⑧ 캐시에 먼저 반영한 값으로 화면을 넘기지 않기**

- 문제: 끝난 대응을 다시 열면 캐시에 남은 옛 상태로 본문이 먼저 그려져, 승인 · 거절 버튼이 잠깐 보였다가 완료
  화면으로 튀었습니다. 같은 이유로 끝난 대응을 "확인함"으로 되돌리는 요청이 나갈 수도 있었습니다.
- 해결 (3c949c7): 상세는 `isFetchedAfterMount`만 보던 것을 `isSuccess && isFetchedAfterMount`(이번 진입에서
  성공한 응답)로 바꾸고, 판단이 설 때까지 본문 대신 로더를 그립니다. 이동 안내 화면이 캐시 상태를 보고 다른 화면으로
  넘기는 판단은 도착 요청이 idle일 때만 합니다. 도착 직후의 완료 상태는 낙관적 업데이트로 먼저 써 둔 값이라, 그걸로
  넘기면 서버가 거절해도 완료 화면이 뜨기 때문입니다. 요청이 실패했을 때 캐시를 되돌리는 것은 조건 없이 합니다.

**⑨ 앱이 꺼진 상태에서 푸시를 눌렀을 때의 화면 이동**

- 앱이 꺼진 상태에서 푸시를 누르면 이동할 화면이 아직 등록되지 않아, React Navigation이 링크를 버리고 홈만
  열립니다. 링크를 보관해 두었다가 화면이 준비된 뒤 이동하도록 처음부터 설계했습니다(이 부분은 전후 코드가 없습니다).
- 전 → 후 (e51e691): 서버가 `data.url`에 담은 주소를 그대로 열던 것 → 서버는 앱 안의 경로(`dispatch/DP-1`)만
  보내고, 스킴이나 `//`로 시작하는 값은 버린 뒤 앱이 스킴을 붙입니다. (딥링크 9개 경로 · 알림 3종)

**⑩ 한 번도 뜬 적 없던 업데이트 안내 (02f0390 · d0c624f)**

- 문제: 버전 점검이 없는 주소 `/api/version/`을 불러 404 → 점검 실패 → 아무것도 안 띄움으로 흘러가, 업데이트
  모달이 한 번도 뜨지 않았습니다. 버전 응답은 `staleTime: Infinity`, OTA 검사는 시작할 때 한 번이라 켜 둔 동안
  나온 업데이트도 몰랐습니다.
- 전 → 후: 경로 `/api/version/` → `/app/version/`. `isPostponed`(참/거짓) → `postponedVersion`(미룬 버전)과
  OTA `updateId`를 기억하고 복귀마다 다시 확인. 스토어 열기 실패 표시는 `latest|minSupported|storeUrl` 키에 묶음.
- 결과: 1.0.0 스토어 빌드가 production 브랜치 OTA를 받아 반영하고 업데이트 모달이 뜨는 것까지 실기기에서 확인,
  두 모달 동작은 테스트로 고정(183줄).

**일하는 방식.** 에러를 무시하는 코드 한 줄 때문에 Android 알림이 사라진 것을 실기기에서 발견한 뒤로(⑨), 실패를
삼키지 않습니다. 알림 경로는 실패를 화면(재시도 배너)까지 올려 보내고, 위치 경로의 에러는 배포 버전에서도 로그로
남깁니다.

### 5-2. 침례교 전용앱 · 교회 통합 앱

- **기간** 2025.04 ~ 현재(2026.07부터 유지보수 지원) · **역할** 앱 개발(2인, 설계 · 개발) · **플랫폼** iOS · Android
- **규모** 화면 70개 이상
- **기술** React Native, Expo(bare), TypeScript, React Navigation, TanStack Query, Reanimated, Firebase Messaging

**배경.** 출석 · 헌금 · 주보 · 증명서 발급을 앱 하나로 모았습니다. 화면이 70개를 넘으면서 기능 개발보다
**상태를 어디서 관리할지**가 더 중요해졌습니다. Expo bare 프로젝트라 iOS · Android 네이티브 설정을 직접 관리해야

**① NFC · QR 출석의 중복 처리**

- 문제: 교회에 붙인 태그에는 모두 같은 주소가 들어 있습니다. iOS는 앱이 꺼진 상태에서 열리면 같은 링크가 두 번
  들어오고, Android는 앱으로 돌아올 때마다 링크를 다시 전달해 주소만으로는 중복을 구분할 수 없었습니다.
- 해결: 주소가 아니라 처리 상태로 중복을 판단하도록 바꿨습니다. 대기 중인 요청 1건, 처리 중 여부, 3초 재요청 제한,
  10분 유효시간으로 걸러 내고, 재시도 조건 5가지를 뒀습니다. "오늘 이미 출석했는지"는 앱에서 막지 않았습니다. 앱을
  켜 둔 채 자정을 넘기면 다음 날 출석이 막히는 문제가 생기기 때문입니다.
- 전 → 후 (d718746): 출시 뒤 OTA 리로드 직후, 프로세스에 남아 있던 링크를 새 런타임의 `getInitialURL()`이 한 번
  더 돌려줘 출석이 다시 나갔습니다(메모리의 쿨다운은 리로드로 초기화). 양 플랫폼에서 재현한 뒤, 리로드 직전에
  시각을 남기고 다음 실행에서 10초 안이면 출석 링크를 한 번만 건너뛰게 고쳤습니다. 중복 출석(서버 4003)은
  "관리자에게 문의" 대신 따로 안내합니다.
- 결과: 앱 첫 실행 · 백그라운드 복귀 · 연속 태그 · 비로그인 · OTA 리로드 직후를 양 플랫폼 실기기에서
  확인했습니다. 인터넷이 끊긴 곳에서 태그했다가 연결 시 출석되는 경로는 아직 실기기 검증 전입니다.
  (중복 경로 4가지를 가드 3개로 막음. 태그 중복 가드는 처음부터 이 설계로 만들어 전후 코드가 없습니다.)

**② 동시에 만료돼도 토큰 갱신은 한 번만**

- 문제: 기존 코드(만료 5분 전 선제 갱신 · 재시도 1회는 원래 있었음)는 `isRefreshing` 플래그와 구독자 큐로 갱신을
  묶었는데, 갱신을 시작한 요청이 큐를 비운 다음 자기도 `subscribeTokenRefresh()`로 그 빈 큐를 기다려 영영 끝나지
  않았습니다. 갱신이 실패하면 실패한 요청마다 `redirectToSignIn()`을 불러 로그아웃(토큰 삭제 · 캐시 초기화 ·
  로그인 화면 이동)이 요청 수만큼 반복됐습니다.
- 해결 (b9adad1 · 5c17cd2): 구독자 큐를 걷어내고 진행 중인 갱신 프로미스 하나(`refreshPromise`)를 모든 요청이
  함께 기다리게 했습니다. 세션 만료 처리는 `triggerSessionExpiredOnce()`의 플래그로 한 번만 돌고, 만료 안내 창도
  이때 붙였습니다.
- 결과: 동시에 여러 요청이 만료돼도 토큰 갱신 요청은 1회만 나갑니다. 갱신에 성공하면 원래 요청이 새 토큰으로
  이어지고, 실패하면 서버 메시지를 그대로 화면에 보여 줍니다.

**③ Android targetSdk 36 대응**

- 문제: Google Play 정책에 따라 targetSdk를 36으로 올렸습니다. API 35부터 edge-to-edge가 강제되면서 상태바
  관련 설정이 무시됐습니다. 헤더 계층과 루트 SafeArea는 "Android 상단 여백은 0"이라는 전제로 고정 10dp만
  비우고 있어서(`topInset = isAndroid ? ANDROID_TOP_SPACING : insets.top`), 헤더가 상태바와 겹쳤습니다.
- 해결 (54bbfc5): 플랫폼이 아니라 SDK 35를 기준으로 네이티브(`MainActivity`)와 JS(`IS_EDGE_TO_EDGE`)가 같은 값을
  보도록 정리했습니다(`topInset = IS_EDGE_TO_EDGE ? insets.top : 0`). edge-to-edge 환경에서는 헤더가 상태바
  높이만큼 여백을 두고, 그 이전 버전에서는 여백을 두지 않아 여백이 두 번 들어가는 문제를 막았습니다.
- 결과: 모든 헤더가 같은 계산식을 써서 높이가 어긋나지 않습니다. 이전 버전 환경은 최신 기기에서 재현해 다시 확인했습니다.

**④ 목록 정렬 · 페이지 구조 개선**

- 원래 주보 · 소식 목록은 1페이지만 보였습니다(페이지 번호 컴포넌트는 있었지만 화면에 연결되지 않음). 리디자인하며
  정렬을 붙였는데 서버가 정렬을 지원하지 않아, 총 페이지 수부터 거꾸로 읽는 임시 우회로를 만들었습니다. 다음 날
  서버에 sort 파라미터를 요청해 `initialPageParam: isReverseRead ? totalPages : 1` → `initialPageParam: 1`로
  바꾸고 역순 읽기를 걷어냈습니다(9db1fbc). 페이지 번호 버튼은 무한 스크롤로 바꿨습니다. (삭제한 모듈 3개 · 테스트 9건)

**⑤ 인터넷이 멀쩡한데 뜨던 오프라인 화면 (5c71916)**

- 문제: iOS 네이티브는 `isInternetReachable`을 주지 않아, NetInfo가 JS에서 구글 도메인(`generate_204`)에 요청을

  떴습니다. 복구 때 화면이 오프라인이 아니면 `return`해 플래그가 굳는 결함, 복귀 직후의 false를 버려 진짜
  오프라인을 놓치는 결함도 함께 나왔습니다.
- 전 → 후: `index.js`에서 `` NetInfo.configure({ reachabilityUrl: `${API_URL}/health`, … }) ``로 판정 기준을 앱

  남은 시간만큼 미룸, 복구는 `isInternetReachable === true` 확정일 때만.
- 결과: `/health`는 인증 없이 95ms에 200. iOS 실기기에서 진입 정상. 증상이 간헐적이라 닫지 않고 재발을 지켜봅니다.

**⑥ 재설치 뒤 반복되던 간편 로그인 실패 (497932d · 4003fdf · eeebd5c)**

- 문제: Keychain은 재설치 뒤에도 남고 AsyncStorage는 지워져, 봉인만 살아남아 지문을 찍은 뒤에야 실패했습니다.

  봉인이 지워지지 않아 매 실행 반복됐습니다. 로그인은 FCM 토큰을 캐시에서만 읽어 재설치 직후 거절됐습니다.
- 전 → 후: 봉인은 있는데 `BIOMETRIC_PROMPTED_ACCOUNT` 기록이 없으면 인증 전에 봉인 삭제, 복호화 실패 문구를
  `"invalidated"`로 분류, `getToken(FCM_TOKEN)` → 캐시가 비면 SDK `getToken`으로 폴백.
- 결과: Galaxy S24+(API 36) · iOS 실기기에서 재설치 후 첫 실행에만 무효화 안내 1회, 이후 프롬프트 없음.

**⑦ 앱 전체 모달을 멈추던 전역 모달 큐 (701d43d · 93eb171 · 6ee5ad5)**

- 문제: 콜드 스타트 직후 iOS가 네이티브 모달 present를 조용히 무시하는데 라이브러리는 표시 완료 이벤트를 보내,
  닫힘 이벤트가 오지 않아 큐가 통째로 잠겼습니다(바텀시트까지). 큐도 `currentRef`를 effect로 늦게 갱신해 같은
  tick의 두 번째 `open()`이 첫 모달을 덮어쓰고 그 Promise가 끝나지 않았습니다. 이후 Android에서는 모달이 떠
  있어도 뒤로가기가 앱 종료 토스트로 빠졌습니다(`BackHandler` 역순 호출 + 종료 핸들러의 재등록).
- 원인 확정: 4초 지연 시 100% 정상(실패 1.2초 · 성공 4.8초), Release 빌드에서도 재현, 스플래시 · 내비게이션
  준비(605ms · 599ms)는 실패 시점(1192ms)보다 앞 — 배제한 가설 5개를 문서로 남김.
- 전 → 후: `ConfirmModal`에 `coverScreen={false}`, 큐 state → `queueRef` + `setCurrentSynced`(ref와 state 동시
  갱신) + 줄이 있으면 뒤에 서기, 뒤로가기 리스너는 마운트 때 한 번 → `current`가 있을 때만 등록.
- 결과: 콜드 스타트 출석 결과가 뜨고 큐가 잠기지 않습니다. 뒤로가기 수정은 정적 검증만, Android 실기기는 미확인.

**⑧ 성도증 캡처 방지 복원과 전환 걸림 (1ebb1d5 · a2d9c9b)**

- 문제: 캡처 방지가 사유 없이 주석 처리돼 있었고, 원 코드에 결함 셋(순서 값을 `&`로 검사해 `UNKNOWN(5)` ·
  `END_RECORDING(2)`까지 경고, 확인으로 닫을 때만 중복 방지 플래그 해제, 탭 번호만 보는 포커스 판정)이 있었습니다. 복원 뒤
  일부 iOS 기기에서 성도증 진입 · 뒤로가기가 한 번 걸렸습니다 — 캡처 방지 토글이 창 레이어를 재합성하는 시점이
  전환 첫 프레임과 겹쳤고, 진행 막대가 `width` 보간이라 JS 스레드를 점유했습니다.
- 전 → 후: `e !== CAPTURED && e !== RECORDING`만 경고, 플래그는 `finally`에서 해제, `useIsFocused()` 결합.
  `prevent()`는 `navigate` 직전으로 앞당기고 `allow()`는 `InteractionManager.runAfterInteractions`로 전환 뒤로,
  진행 막대는 `transform: scaleX` + 네이티브 드라이버.
- 결과: 복원은 양 플랫폼 실기기 확인. 전환 걸림 수정은 정적 검증만 거쳤습니다.

**그 밖에.** 서버 데이터는 TanStack Query, 로그인 세션과 전역 모달은 Context 두 개, 나머지는 각 화면에서 관리합니다.
NFC · QR 링크, 푸시 알림, 결제 웹뷰 복귀는 하나의 훅에서 처리합니다. 결제 웹뷰를 Android까지 통일하면서 뒤로가기
버튼 동작을 정리했고, 기존 색상 키 사용처 약 500곳(120여 개 파일)을 그대로 둔 채 의미 계층만 얹어 디자인 토큰을 도입했습니다. Provider 순서를 바꾸면
에러 없이 기능이 사라지는 부분(예: 백그라운드 푸시 핸들러를 App.tsx로 옮기면 앱이 꺼져 있을 때의 푸시를 못 받음)을 문서로 정리했습니다.

### 5-4. Plus SMS · 대량 문자 발송 웹 서비스

**① 대량 목록 가상화 (ea54eec)**

**② 다양한 형식의 전화번호 정리 (2fc156f · 6b1b659)**

- 처음 판정은 길이(9~12자리)만 봐서 02 유선 번호도 통과했고, 정규식으로 바꾸는 중에는 중복 비교가 정규화 전
  모양끼리로 돌아가 010과 +82로 적은 같은 번호가 따로 등록될 수 있었습니다.
- 전 → 후: `includes(phone)` → 국가번호를 붙인 `finalPhone`끼리 비교. 공백으로 자른 조각을 숫자 10자리가 될 때까지
  이어 붙이고 82/12자리 · 10/10자리를 010 꼴로 맞춘 뒤 `/^01[016789]\d{7,8}$/`로 판정.
- 입력 필터 (7bc73b1 → 8d1174a): 입력창이 `/^[0-9,\n,-]*$/`에 맞지 않는 값을
통째로 버려서, 공백 · `+` · 괄호가 섞인 명단을 붙여넣으면 아무 반응이 없었습니다. 허용 문자를 넓히다가 결국 필터를
없애고 모든 판정을 파서에 넘겼습니다. 틀린 번호는 이제 오류 목록으로 갑니다.

**③ 엑셀로 올린 명단만 통째로 오류가 되던 문제 (2fc156f · 6b1b659 · d334eb5)** 파서를 공백 분리로 바꾸자 셀을 콤마로 이어
넘기던 엑셀 입력만 한 덩어리가 됐습니다. 파서에 콤마를 되살리는 대신 셀을 줄바꿈으로 이어 입력창과 같은 모양으로
넘겨, 직접 입력과 같은 검증 함수를 거치게 했습니다. 엑셀은 A열 2행부터가 아니라 첫 시트에서 숫자가 든 모든 셀을 읽습니다.

**④ 잘못된 번호만 따로 관리 (af28c92 · 6a40440)** 한 건이라도 틀리면 `alert`로 전체를 막던 것을 등록 · 중복 ·
오류로 나눠, 문제 번호만 복사하거나 엑셀로 내려받게 했습니다. 입력 방식을 바꾸면 세 목록을 함께 초기화합니다.

**⑤ 포인트 부족 시 발송 전 차단 (ef43251 · af28c92)** 단가는 API로, 보유 포인트는 로그인 정보에서 읽어 목록이
바뀔 때마다 결제 포인트를 다시 계산하고, 부족하면 전송 버튼을 막고 충전 안내를 띄웁니다. 5만 건 상한은 이미 쌓인
건수와 합쳐 추가할 때 한 번, 발송할 때 한 번 더 확인합니다.

**⑥ 하나의 코드로 두 브랜드 운영 (b874e8b · abadeae · ab6b997)** 컴포넌트에 박혀 있던 로고 · 상호 · 페이지 제목을 한 파일에
모으고 `VITE_DOMAIN` 값 하나로 고릅니다. Jenkins는 한 번 받은 코드를 브랜드별 폴더에 복사해 각자의 `.env`로 따로
빌드합니다. 지금 상수는 두 브랜드 중 하나를 고르는 모양이라, 브랜드가 늘면 표 형태로 바꿔야 합니다.

**남은 개선점.** 입력창 안내 문구에 아직 "콤마로 구분"이 남아 있어, 다시 작업한다면 안내 문구부터 파서와 맞출 계획입니다.

### 5-5. 포트폴리오 사이트 · 개인 프로젝트

- **기간** 2026.07 ~ 2026.09 · **역할** 기획 · 디자인 · 개발
- **링크** https://limjeongsik-portfolio.vercel.app
- **기술** React 19, Vite 8, TypeScript, Tailwind CSS v4, AI SDK + Gemini, Vercel, Bun, Biome

**읽히는 화면.** 처음에는 Three.js 3D 공간과 스크롤 연출로 만들었다가, 가독성을 해친다는 판단으로 모션 라이브러리와
3D를 모두 걷어냈습니다. 지금은 무채색 바탕에 색은 프로젝트에만 쓰고, 움직임은 첫 화면 등장 하나를 빼면 사용자의 행동에 답하는
것만 CSS로 남겼습니다. 프로젝트 상세에는 사례마다 원 저장소의 전 · 후 코드와 커밋을 근거로 붙였습니다.

**AI 안내 챗봇.** 방문자의 질문에 답하면서 해당 화면으로 안내하는 챗봇입니다. 섹션 이동 · 페이지 이동 · 정보 카드
표시 등 7가지 도구를 사용합니다. 사이트 데이터(`src/data`)에서 답변용 정보를 자동으로 만들어, 챗봇이 사실과 다른
이력을 말하지 않게 했습니다.

- 보안: API 키는 서버에서만 사용하고, 프롬프트 주입 요청(400)과 과도한 크기의 요청(413)을 차단합니다. 분당 요청은
  20회로 제한하고, 포트폴리오와 관계없는 질문에는 짧게 답을 거절합니다.
- 성능: 챗봇 코드(534KB)는 버튼에 마우스를 올렸을 때만 불러옵니다.
- 검증: 헤드리스 브라우저로 7가지 도구를 모두 실행해 확인했고, 배포 환경 응답 시간은 1.3초입니다.
