## 3. 핵심 역량

### 3-1. 웹과 앱을 모두 개발합니다

- React 웹(Vite · Next.js)과 React Native 앱(Expo managed · **Expo bare**)을 모두 실제 서비스로 출시했습니다.
- 웹 페이지가 앱의 WebView 안에서 동작하는 서비스에서 앱과 웹이 서로 신호를 주고받는 **브릿지**를 양쪽 모두 설계했습니다(아이머그).
- iOS · Android 네이티브 폴더를 직접 관리하는 Expo bare 프로젝트에서 Android 정책 변경(targetSdk 36)에 대응했습니다(침례교 전용앱).

### 3-2. 라이브러리로 해결되지 않으면 네이티브까지 직접 다룹니다

- 알림 라이브러리로 무음 모드를 우회할 수 없어 **Kotlin으로 Expo 네이티브 모듈**을 만들어 긴급 알림 채널을 직접 생성했습니다(SafeOps).
- 긴급 알림 여부를 앱이 추측하지 않고 **서버가 보내는 데이터로 판단**하도록 앱과 서버의 역할을 나눴습니다(SafeOps).
- edge-to-edge 전환으로 틀어진 상단 여백을 **SDK 35 기준값 하나**로 네이티브와 JS가 함께 쓰도록 정리했습니다(침례교 전용앱).

### 3-3. 인증과 상태 관리를 안정적으로 설계합니다

- 여러 요청이 동시에 만료돼도 **토큰 갱신은 한 번만** 일어나도록 했습니다(침례교 · 아이머그 · Plus SMS).
- 토큰이 만료되기 전에 **미리 갱신**합니다: 만료 5분 전(침례교 · Plus SMS), 남은 시간 30초 · 60초 기준(아이머그).
- 보호자와 아이가 계정 하나를 함께 쓰는 서비스에서 **토큰을 4종으로 나눠** 관리했습니다(아이머그).
- 여러 사람이 한 기기를 쓰는 앱에서 **로그아웃 시 토큰 · 캐시 · 위치 정보를 한 번에 초기화**했습니다(SafeOps).
- 서버 데이터는 TanStack Query, 로그인 세션과 전역 모달은 Context, 나머지는 각 화면에서 관리하도록 나눕니다.
- 같은 값을 화면마다 따로 계산하다 결과가 어긋난 문제를 **계산 함수 하나로 통합**해 해결했습니다(SafeOps).

### 3-4. 측정하고, 실제 기기로 검증하고, 문서로 남깁니다

- 성능은 먼저 측정한 뒤 개선합니다: 10,000건 렌더링 **1,300.9ms → 32.6ms**(Plus SMS).
- 기준값은 실측으로 정합니다: 실내 GPS 갱신 간격 **7~185초**를 측정해 필터 기준(10분 · 5초)을 정했습니다(SafeOps).
- 실제 기기에서 확인합니다: 무음 상태에서 앱 실행 중 · 백그라운드 · 종료 세 가지 경우를 양 플랫폼에서 확인했습니다(SafeOps).
  NFC 출석도 앱 첫 실행 · 백그라운드 복귀 · 연속 태그 · 비로그인 상태를 실제 기기에서 확인했습니다(침례교).
- 테스트로 품질을 관리합니다: **테스트 1,006개(84 suites)**, 테마 글자 대비 기준도 테스트로 검증합니다(SafeOps).
- 순서를 바꾸면 조용히 기능이 깨지는 부분(Provider 순서 등)을 문서로 남깁니다(침례교).

## 5. 프로젝트 상세

각 프로젝트는 **개요 → 배경 → 문제 · 해결 · 결과** 순서입니다. 면접에서 "가장 어려웠던 문제"를 물으면
각 프로젝트의 첫 번째 사례부터 이야기하면 됩니다.

### 5-1. SafeOps · 행사 현장 경비 근무 앱

- **소속** 센티언트 시스템즈 플랫폼 엔지니어링 팀
- **기간** 2026.07 ~ 현재 · **역할** 앱 개발(설계 · 개발) · **플랫폼** iOS · Android
- **성과** App Store · Google Play 출시(현재 1.0.2) · 라이트/다크 테마 · 테스트 1,006개(84 suites)
- **기술** React Native, Expo, TypeScript, TanStack Query, React Navigation, FCM · Notifee,
  Expo Modules(Kotlin), 네이버 지도 SDK, EAS Update

**배경.** 경비 인력은 근무 중 무전기를 들고 이동하고, 휴대폰은 주머니에 넣어 둡니다. 사용자가 앱을 열어야
동작하는 일반적인 앱과 달리, **앱을 열지 않아도 동작해야** 했습니다. 계정은 관제실이 발급하고 근무가 끝나면
닫으며, 야간 근무가 많아 테마도 두 가지가 필요했습니다.

**① 위치 전송 상태를 정확하게 표시**

- 문제: 전송 성공 여부만 보면 앱은 항상 정상으로 보였습니다. 그런데 GPS 측정에 실패하면 보낼 좌표가 없어서,
  관제실은 위치를 받지 못하는데 화면은 정상으로 표시됐습니다. 또 홈과 설정 화면이 같은 상태 표시를 따로
  계산해, 근무가 끝난 뒤에도 설정 화면에만 경고가 남아 있었습니다.
- 해결: 화면이 보는 기준을 "관제실이 마지막으로 위치를 받은 시각"으로 바꿨습니다. 근무가 끝나면 전송과 GPS를
  함께 멈추고, 두 화면의 계산은 함수 하나로 합쳤습니다.
- 위치 필터: 10초마다 측정한 좌표에서 10분 넘은 좌표, 이전 위치로 튄 좌표(3회 연속일 때만 인정), 중복 좌표(5초가
  지나면 다시 전송)를 걸러 냅니다. 오래된 좌표 기준은 처음에 90초였는데, 실내에서 GPS 갱신 간격을 측정해 보니
  7~185초로 들쭉날쭉해 전부 걸러지는 문제가 있어 10분으로 늘렸습니다. 모든 좌표가 걸러져도 10초마다 마지막 좌표를
  다시 보냅니다.
- 결과: 위치 전송이 끊기면 홈 화면에 바로 표시되고, 근무가 끝나면 홈과 설정 화면이 동시에 근무 종료로 바뀝니다.
  (전송 주기 10초 · 전송 중단 감지 3분)

**② 무음 모드에서도 울리는 긴급 알림**

- 문제: 긴급 지시는 벨소리를 꺼 둬도 울려야 합니다. 알림 채널을 나눠 방해 금지 모드는 통과했지만 무음 모드는
  통과하지 못했습니다. 무음 모드에서는 알림 소리가 꺼지기 때문에 알람 소리로 보내야 하는데, 사용하던 알림
  라이브러리에는 이 설정을 넣을 방법이 없었습니다.
- 해결: 긴급 알림 채널만 Kotlin으로 만든 Expo 네이티브 모듈에서 알람 용도로 직접 생성했습니다. Android 알림 채널은
  한 번 만들면 소리 설정을 바꿀 수 없어 채널 ID를 새로 만들었습니다. 삼성 기기는 벨소리 모드에서 한 번 더 막아서,
  무음 · 진동 모드일 때만 앱이 직접 알람 소리와 진동을 냅니다. 긴급 여부는 앱이 아니라 **서버가 보내는 데이터**로
  판단합니다.
- 결과: Android · iOS 실기기에서 무음 상태의 앱 실행 중 · 백그라운드 · 종료 세 가지 경우를 모두 확인했습니다.
  채널 생성에 실패하면 홈 화면에 다시 시도 안내를 띄웁니다.

**③ 라이트 · 다크 테마**

- 문제: 스타일 코드가 색상 값을 직접 참조하고 있어 테마를 바꿀 수 없는 구조였습니다.
- 해결: 모든 스타일을 색상 팔레트를 받아 만들어지는 구조로 바꿨습니다. 두 테마는 같은 색상 이름을 쓰고, 상태 색은
  색감은 유지하면서 밝기만 바꿨습니다. 글자 대비(일반 글자 AA 4.5:1, 색 배경 위 글자 3:1)는 테스트로 검증합니다.
  시스템 테마 연동은 네이티브를 다시 빌드해야 해서 이미 배포된 앱에는 적용할 수 없기 때문에, 설정 화면에서 고르는
  방식으로 만들어 **EAS Update(OTA)** 로 배포했습니다.
- 결과: 테마를 바꾸면 지도까지 야간 색상으로 함께 바뀝니다.

**④ 낙관적 업데이트의 되돌리기 조건 정리**

- 서버 응답을 기다리면 화면 반응이 늦어져 사용자가 버튼을 다시 누르는 문제가 있어, 화면을 먼저 바꾸고 실패하면
  되돌리도록 했습니다. 다만 조건 없이 되돌리면 서버가 거절해도 완료 화면이 뜨는 문제가 있어, 요청이 끝난 상태에서만
  되돌리도록 했습니다.

**⑤ 앱이 꺼진 상태에서 푸시를 눌렀을 때의 화면 이동**

- 앱이 꺼진 상태에서 푸시를 누르면 이동할 화면이 아직 준비되지 않아 링크가 무시되고 홈만 열렸습니다. 링크를
  보관해 두었다가 화면이 준비된 뒤 이동하도록 바꿨습니다. 보안을 위해 외부 주소 전체가 담긴 링크는 받지 않습니다.
  (딥링크 9개 경로 · 알림 3종)

**⑥ 여러 사람이 한 기기를 쓰는 환경 대응**

- 교대 근무로 한 기기를 여러 사람이 쓰는데, 로그아웃 후 다음 사람이 로그인하면 이전 사람의 데이터가 보일 수
  있었습니다. 로그아웃하거나 인증이 만료(401 · 403)되면 토큰 · 캐시 · 위치 정보를 한 번에 초기화하도록 했습니다.

**일하는 방식.** 에러를 무시하는 코드 한 줄 때문에 Android 알림이 사라진 것을 실기기에서 발견한 뒤로, 알림과 위치
관련 에러는 배포 버전에서도 로그로 남깁니다.

### 5-2. 침례교 전용앱 · 교회 통합 앱

- **기간** 2025.04 ~ 현재 · **역할** 앱 개발(2인, 설계 · 개발) · **플랫폼** iOS · Android
- **규모** 화면 100개 이상
- **기술** React Native, Expo(bare), TypeScript, React Navigation, TanStack Query, Reanimated, Firebase Messaging

**배경.** 출석 · 헌금 · 주보 · 증명서 발급을 앱 하나로 모았습니다. 화면이 100개를 넘으면서 기능 개발보다
**상태를 어디서 관리할지**가 더 중요해졌습니다. Expo bare 프로젝트라 iOS · Android 네이티브 설정을 직접 관리해야
했습니다.

**① NFC · QR 출석의 중복 처리**

- 문제: 교회에 붙인 태그에는 모두 같은 주소가 들어 있습니다. iOS는 앱이 꺼진 상태에서 열리면 같은 링크가 두 번
  들어오고, Android는 앱으로 돌아올 때마다 링크를 다시 전달해 주소만으로는 중복을 구분할 수 없었습니다.
- 해결: 주소가 아니라 처리 상태로 중복을 판단하도록 바꿨습니다. 대기 중인 요청 1건, 처리 중 여부, 3초 재요청 제한,
  10분 유효시간으로 걸러 내고, 재시도 조건 5가지를 뒀습니다. "오늘 이미 출석했는지"는 앱에서 막지 않았습니다. 앱을
  켜 둔 채 자정을 넘기면 다음 날 출석이 막히는 문제가 생기기 때문입니다.
- 결과: 인터넷이 끊긴 곳에서 태그해도 요청을 보관해 두었다가 연결되는 즉시 출석이 처리됩니다. 앱 첫 실행 ·
  백그라운드 복귀 · 연속 태그 · 비로그인 상태를 양 플랫폼 실기기에서 확인했습니다.

**② 동시에 만료돼도 토큰 갱신은 한 번만**

- 해결: 진행 중인 갱신 요청이 있으면 다른 요청은 새로 갱신하지 않고 그 결과를 함께 기다리게 했습니다. 만료 5분
  전에 미리 갱신하고, 재시도는 한 번만 하며, 세션 만료 안내 창이 여러 번 뜨지 않게 막았습니다.
- 결과: 동시에 여러 요청이 만료돼도 토큰 갱신 요청은 1회만 나갑니다. 갱신에 성공하면 원래 요청이 새 토큰으로
  이어지고, 실패하면 서버 메시지를 그대로 화면에 보여 줍니다.

**③ Android targetSdk 36 대응**

- 문제: Google Play 정책에 따라 targetSdk를 36으로 올렸습니다. API 35부터 edge-to-edge가 강제되면서 상태바
  관련 설정이 무시되고, 상단 여백을 0으로 가정한 기존 코드가 앱 전체에서 어긋났습니다.
- 해결: SDK 35를 기준으로 네이티브와 JS가 같은 값을 보도록 정리했습니다. edge-to-edge 환경에서는 헤더가 상태바
  높이만큼 여백을 두고, 그 이전 버전에서는 여백을 두지 않아 여백이 두 번 들어가는 문제를 막았습니다.
- 결과: 모든 헤더가 같은 계산식을 써서 높이가 어긋나지 않습니다. 이전 버전 환경은 최신 기기에서 재현해 다시 확인했습니다.

**④ 목록 정렬 · 페이지 구조 개선**

- 서버가 정렬을 지원하지 않아 마지막 페이지부터 거꾸로 읽던 구조를, 서버에 정렬 기능을 요청해 바꾸고 관련 코드를
  삭제했습니다. 페이지 번호 버튼은 무한 스크롤로 바꿨습니다. (삭제한 모듈 3개)

**그 밖에.** 서버 데이터는 TanStack Query, 로그인 세션과 전역 모달은 Context 두 개, 나머지는 각 화면에서 관리합니다.
NFC · QR 링크, 푸시 알림, 결제 웹뷰 복귀는 하나의 훅에서 처리합니다. 결제 웹뷰를 Android까지 통일하면서 뒤로가기
버튼 동작을 정리했고, 기존 색상 코드 275곳을 그대로 둔 채 디자인 토큰을 도입했습니다. Provider 순서를 바꾸면
에러 없이 기능이 사라지는 부분(예: 세션 만료 안내가 뜨지 않음)을 문서로 정리했습니다.

### 5-3. 아이머그 · 키즈 영상 서비스

- **기간** 2024.08 ~ 2025.05 · **역할** 프론트엔드(초기 설계 · 주요 화면 · API 연동) · **플랫폼** 모바일 웹 + 앱 WebView
- **링크** https://m.i-mug.co.kr
- **기술** React, TypeScript, Vite, TanStack Query, Zustand, styled-components, Axios (배포: Jenkins → Nginx)

**배경.** 보호자가 시청 규칙을 정하고 아이가 그 안에서 영상을 봅니다. 계정은 하나지만 사용자는 둘입니다. 또 웹으로
만들었지만 iOS · Android 앱의 WebView 안에서도 동작해서, 영상 재생 명령이 앱에서 들어오기도 합니다.

**① 보호자와 아이를 구분하는 토큰 4종 인증**

- Access(서비스 이용) · Refresh(재발급) · 아이 프로필 · 보호자 2차 인증 토큰을 나눴습니다. 하나가 만료돼도 다른
  기능에는 영향이 없고, 보호자 설정 화면에 들어갈 때만 2차 인증을 요구합니다.
- 요청을 보내기 직전 남은 시간이 30초(2차 인증은 60초)보다 적으면 먼저 갱신합니다.
- 동시에 여러 요청이 갱신을 시도해도 실제 갱신은 한 번만 일어나게 했습니다.
- 아이 프로필 토큰이 없으면 프로필 선택 화면으로 보내고, 2차 인증 토큰이 만료되면 로그아웃 없이 해당 토큰만 지웁니다.

**② 앱과 웹 사이의 영상 제어 통합**

- 문제: 앱에서 영상을 멈춰도 플레이어와 시력 보호 화면이 서로 다르게 동작했고, iOS와 Android의 호출 방식이 달라
  화면마다 코드를 두 벌씩 갖고 있었습니다.
- 해결: 영상 제어를 하나의 훅으로 모았습니다. 앱이 호출할 함수를 등록해 두고, 이 함수가 재생 · 스크롤 잠금 · 시력
  보호 화면 · 쇼츠 정지 상태를 한 번에 처리합니다. 웹에서 앱으로는 재생 중인지 여부만 전달하고, 일반 브라우저에서는
  이 과정 없이 그대로 재생됩니다.

**③ 멘션 · 영상 시간 댓글 입력**

- 댓글에 @멘션과 영상 시간(01:23)을 하나의 블록으로 넣기 위해 contentEditable로 입력창을 만들었습니다. 변환 후
  커서 위치를 되돌리고, 한글을 조합하는 중에는 변환을 멈춰 글자가 깨지지 않게 했습니다.

**④ 최근 검색어 중복 정리** 앞뒤 공백을 정리하고 중복을 제거했으며, 한글 조합 중 Enter는 무시하도록 했습니다.

**⑤ 쇼츠 재생 제어** 목록은 무한 스크롤로 이어 받고, 다음 페이지를 미리 불러옵니다. 화면에 보이는 영상만 재생하고,
시청 시간이 끝나면 제한 안내를 띄웁니다.

### 5-4. Plus SMS · 대량 문자 발송 웹 서비스

- **기간** 2024.11 ~ 2025.04 · **역할** 프론트엔드 1인(설계 · 개발 · API 연동 · 유지보수) · **플랫폼** 웹
- **링크** https://www.plus-sms.com
- **기술** React, TypeScript, Vite, TanStack Query, Zustand, styled-components, react-window, xlsx, Jenkins

**배경.** 고객 명단은 엑셀, 메신저, 다른 시스템에서 복사돼 형식이 제각각입니다. 한 번에 최대 5만 건을 보내고,
발송하는 순간 비용이 나갑니다. 같은 서비스를 Plus SMS와 Modoo SMS 두 브랜드로 운영합니다.

**① 대량 목록 렌더링 성능 개선**

- 렌더링 시간을 먼저 측정한 뒤 react-window로 화면에 보이는 줄만 그리도록 바꿨습니다. 번호 칩의 줄바꿈 때문에 줄
  높이가 일정하지 않던 문제는 번호 세 개를 한 줄로 묶어 해결했고, 화면 크기가 바뀌면 줄 높이를 다시 계산합니다.
- 결과: **10,000건 기준 평균 렌더링 1,300.9ms → 32.6ms.** 5만 건을 올려도 화면에는 보이는 몇 줄만 그립니다.

**② 다양한 형식의 전화번호 정리**

- 숫자만 뽑아 길이로 판단하던 방식을 별도 파서로 바꿨습니다. 010-, +82, 괄호 등이 섞인 번호를 010 형식으로 맞춘 뒤
  휴대폰 번호 규칙으로 검사하고, 중복은 국가번호를 붙인 최종 형태로 비교합니다. 같은 사람에게 두 번 발송되는
  문제가 없어졌습니다.

**③ 직접 입력과 엑셀 업로드의 검증 통합** 엑셀 데이터가 콤마로 이어져 전체가 오류 처리되던 문제를, 엑셀 데이터를
직접 입력과 같은 형식으로 바꿔 같은 검증 함수를 거치게 해 해결했습니다.

**④ 잘못된 번호만 따로 관리** 등록 · 중복 · 오류 번호를 따로 관리하고, 문제 번호만 복사하거나 엑셀로 내려받을 수
있게 했습니다. 입력 방식을 바꾸면 세 목록을 함께 초기화합니다.

**⑤ 포인트 부족 시 발송 전 차단** 단가와 보유 포인트를 받아 목록이 바뀔 때마다 결제 포인트를 다시 계산하고,
부족하면 전송 버튼을 막고 충전 안내를 띄웁니다. 5만 건 제한은 추가할 때와 발송할 때 두 번 확인합니다.

**⑥ 하나의 코드로 두 브랜드 운영** 브랜드마다 다른 로고 · 상호 · 페이지 제목을 한 파일에 모으고 `VITE_DOMAIN` 값
하나로 나눠 빌드합니다. Jenkins 배포 시 index.html 파일명에 타임스탬프를 붙이고 심볼릭 링크로 연결해 이전 파일이
캐시에 남지 않게 했습니다.

**남은 개선점.** 입력창 안내 문구에 아직 "콤마로 구분"이 남아 있어, 다시 작업한다면 안내 문구부터 파서와 맞출 계획입니다.

계산합니다. 페이지를 이동할 때도 화면을 새로 그리지 않고 카메라가 이동하며, 동작 줄이기 설정을 켜면 움직임을 줄입니다.

**AI 안내 챗봇.** 방문자의 질문에 답하면서 해당 화면으로 안내하는 챗봇입니다. 섹션 이동 · 페이지 이동 · 정보 카드
표시 등 7가지 도구를 사용합니다. 사이트 데이터(`src/data`)에서 답변용 정보를 자동으로 만들어, 챗봇이 사실과 다른
이력을 말하지 않게 했습니다.

- 보안: API 키는 서버에서만 사용하고, 프롬프트 주입 요청(400)과 과도한 크기의 요청(413)을 차단합니다. 분당 요청은
  20회로 제한하고, 포트폴리오와 관계없는 질문에는 짧게 답을 거절합니다.
- 성능: 챗봇 코드(534KB)는 버튼에 마우스를 올렸을 때만 불러옵니다.
- 검증: 헤드리스 브라우저로 7가지 도구를 모두 실행해 확인했고, 배포 환경 응답 시간은 1.3초입니다.
