# 임정식에 대한 평가 — 포트폴리오 저장소를 근거로

> 채용 담당자와 기술 면접관의 눈으로 이 저장소(`src/data/*.ts`, `docs/PROGRESS.md`, 코드)를 읽고 쓴
> 평가입니다. 칭찬만 모으지 않고 **보완하면 좋은 점**도 같이 적었습니다. 이력서를 고칠 때 체크리스트로 쓰세요.
> 판단의 근거는 항목마다 괄호로 달았습니다.

---

## 1. 한 문단 요약

**앱과 웹 사이, JS와 네이티브 사이, 클라이언트와 서버 사이처럼 경계에서 생기는 문제를 끝까지 파고드는
프로덕트 지향 프론트엔드 개발자.** 화면을 그리는 일보다 "이 상태가 진짜인가", "이 판정은 어디서 하는가",
"실패했을 때 무엇이 남는가"를 먼저 묻습니다. 증거가 수치와 실기기 검증으로 남아 있어서 이야기에 설득력이
있습니다. 시니어 초입~중간 레벨의 앱/웹 겸업 프론트엔드, 또는 소규모 팀의 프론트엔드 리드 포지션에 잘 맞습니다.

---

## 2. 강점 — 근거와 함께

### ① 문제를 "현상"이 아니라 "원인이 있는 층"에서 푼다
- 무음을 뚫지 못한 긴급 알림을 채널 설정의 문제로 보지 않고 **오디오 스트림**의 문제로 다시 정의한 뒤,
  라이브러리가 막힌 지점에서 Kotlin 네이티브 모듈로 내려갔습니다. 채널 속성이 생성 후 바뀌지 않는다는
  OS 동작, 삼성 기기의 벨소리 모드 차이까지 따라갔습니다. (SafeOps 사례 ②)
- 파서를 엑셀에 맞추지 않고 **엑셀 입력을 파서의 모양에 맞춰** 검증 경로를 하나로 만든 판단도 같은
  결입니다. (Plus SMS 사례 ③)

> 면접관이 보기에: "라이브러리가 안 되면 우회하는 사람"이 아니라 "왜 안 되는지 아는 사람". 시니어로
> 보이는 가장 강한 신호입니다.

### ② 판정은 한 곳에서, 상태는 성격별로
- 홈과 설정이 같은 배지를 따로 계산하다 어긋난 문제 → 파생 함수 하나로 통합. (SafeOps ①)
- 번호 규칙은 한 함수, 영상 정지는 한 훅, 앱 밖 입력(딥링크 · 푸시 · 결제 복귀)은 한 훅, 브랜드는 한 값.
  (Plus SMS · 아이머그 · 침례교)
- 서버 상태 / 세션 · 전역 모달 / 화면 로컬로 상태를 세 곳에만 둔 설계. (침례교)

> Single Source of Truth를 말로가 아니라 **실제로 깨졌던 사례**로 설명할 수 있다는 게 강점입니다.

### ③ 인증 흐름 설계를 세 번 이상 반복해 다듬었다
- 단일 비행 갱신, 선제 갱신(5분 전 / 30초 · 60초 임계), 재시도 표시, 만료 처리 래치, 4종 토큰 분리,
  세션 종료 시 캐시 · 위치까지 정리. 프로젝트마다 요구가 다른데 같은 원리를 알맞게 변형했습니다.
  (침례교 ② · 아이머그 ①② · SafeOps ⑥ · Plus SMS)

### ④ 측정하고, 실기기에서 확인하고, 테스트로 고정한다
- 가상화 전에 렌더링 시간부터 쟀습니다: 1,300.9ms → 32.6ms. (Plus SMS)
- 위치 필터 임계값을 실측(실내 측위 7~185초)에서 끌어냈고, 90초였던 값을 근거를 들어 10분으로 고쳤습니다. (SafeOps)
- 테스트 84 suites · 1,006개, 테마 대비를 테스트로 고정. (SafeOps)
- 에러를 삼키지 않는다는 원칙이 실제 사고(빈 catch로 사라진 포그라운드 알림)에서 나왔습니다.

### ⑤ 사용자 맥락에서 기술 결정을 끌어낸다
- "요원은 화면을 보지 않는다" → 열지 않아도 도는 앱. "야간 근무가 절반" → 테마 두 벌. "시스템 테마 연동은
  네이티브 재빌드가 필요해 이미 나간 빌드에 닿지 않는다" → 설정에서 고르게 하고 OTA로 배포. (SafeOps)
- "앱을 끄지 않고 자정을 넘긴 사람은 출석을 못 한다" → 오늘 출석 여부를 앱이 막지 않음. (침례교)

### ⑥ 학습을 제품으로 끝낸다
- 웹 퍼블리셔 → 프론트엔드 → React Native 앱 출시 → Kotlin 네이티브 모듈까지, 성장 곡선이 이력 자체로
  보입니다. 포트폴리오도 Three.js 3D 공간과 도구를 쓰는 AI 안내자, 그리고 그 안내자의 보안(주입 거부 ·
  본문 크기 제한 · 레이트리밋)까지 직접 만들었습니다.

### ⑦ 문서화 습관
- `PROGRESS.md`의 "함정 노트", Provider 순서 중 "바꾸면 조용히 깨지는 곳" 문서화 등 **다음 사람(과
  미래의 자신)을 위한 기록**이 몸에 배어 있습니다. 팀 리드 역할과 잘 맞는 습관입니다.

## 3. 보완하면 좋은 점 — 이력서 기준

면접에 불리하게 작용할 수 있는 순서대로 적었습니다.

### ① 경력 항목이 프로젝트 항목보다 훨씬 얇다 ★
프로젝트 설명은 아주 구체적인데 경력 성과는 "공용 인스턴스 설계 및 구현", "기술 역량 향상에 기여"처럼
어느 이력서에나 있을 법한 문장입니다. 두 회사에서 같은 문장이 반복되기도 합니다.
- **"공용 인스턴스"가 무엇인지 풀어 쓰기.** 예: "웹 · 앱이 공유하는 Axios 인스턴스 — 토큰 선제 갱신 ·
  단일 비행 · 에러 정규화" (실제 내용에 맞게).
- **리드로서의 결과를 숫자나 사례로.** 팀 규모(몇 명), 리뷰 규칙을 어떻게 바꿨는지, 스터디를 몇 회 했는지,
  신규 입사자 온보딩 기간이 어떻게 바뀌었는지 등.
- **"리드타임 30% 단축"의 측정 기준**을 한 줄 덧붙이기(무엇을 기준으로 몇 일 → 몇 일). 면접에서 반드시 물어봅니다.

### ② 프로젝트와 소속 회사가 연결돼 있지 않다 ★
SafeOps는 센티언트 시스템즈 소속으로 연결했습니다. 나머지(침례교 · 아이머그 · Plus SMS)는 기간이 회사
재직 기간과 겹치지만 어느 회사 소속 프로젝트인지 적혀 있지 않습니다.
(`content.js`의 `org`, `resume.md`의 TODO 자리.) 연결하면 "팀 리드 시절 무엇을 만들었나"가 한눈에 보입니다.
외주 프로젝트라면 외주라고 밝히는 편이 오히려 신뢰를 줍니다.

### ③ 외주 프로젝트에 기간 · 소속이 없다
2025년 이력서의 외주 작업 16건을 "외주 프로젝트" 섹션으로 옮겨 프리랜서 구간이 비어 보이던 문제는
덜었습니다. 다만 원문에 날짜가 없어 어느 것이 모과플레이 외주이고 어느 것이 프리랜서 시절인지 알 수
없습니다. 기간을 알면 항목마다 적고, 바이블25 · 엠그로브처럼 기술 이야기가 있는 한두 건은 주요
프로젝트 형식(문제 · 해결 · 결과)으로 키워 볼 만합니다.

### ④ 접근성 "WCAG AA 충족"은 근거를 준비해 두기
두 회사에서 같은 문장이 나옵니다. 어떤 도구로 점검했는지, 무엇을 고쳤는지(대체 텍스트, 키보드 초점,
대비 등) 한두 가지를 준비해 두세요. 근거가 약하면 차라리 "접근성 개선(대체 텍스트 · 키보드 탐색 · 대비)"
처럼 한 일을 적는 편이 안전합니다.

### ⑤ 사용자 규모 · 비즈니스 결과가 없다
기술 수치는 풍부하지만 "몇 명이 쓰는지", "스토어 평점", "문의가 줄었는지" 같은 결과 지표가 없습니다.
공개 가능한 범위에서 하나라도 있으면 프로덕트 감각이 더 강하게 보입니다.

### ⑥ 기본 정보 빈칸
- GitHub · 블로그 링크가 포트폴리오 사이트에서도 자리표시자(`@username`)입니다.
- 학력 · 자격 · 교육 항목이 없습니다. 비전공이라면 오히려 "웹 퍼블리셔부터 시작한 성장 곡선"이
  강점이 되니 숨기지 말고 적으세요.

### ⑦ 원문 표기 (반영 완료)
"주도 했습니다" 띄어쓰기, "바움루트미주식회사"처럼 붙은 회사명, "프로젝트 성공적으로 완료"의 조사 누락은
사이트(`src/data/experience.ts`)와 이력서 양쪽에 고쳐 넣었습니다.

## 4. 포지셔닝 제안

| 지원 방향 | 앞에 둘 이야기 | 이력서에서 조정할 것 |
|---|---|---|
| React Native 앱 개발 | SafeOps(알림 · 위치 · 네이티브 모듈), 침례교(bare · targetSdk) | 프로젝트 순서 그대로, 핵심 역량 ①② 강조 |
| 웹 프론트엔드 (B2B · 대용량 데이터) | Plus SMS(가상화 · 파서 · 결제 차단), 아이머그(인증 · 브릿지) | `content.js`에서 Plus SMS를 맨 앞으로 |
| 하이브리드 (웹 + 앱 WebView) | 아이머그 브릿지, 침례교 결제 웹뷰 | 핵심 역량 ① 제목을 "하이브리드"로 |
| 프론트엔드 리드 | 경력의 팀 리드 2회 + 문서화 습관 + 판정은 한 곳에서 | 보완점 ①을 먼저 채워야 설득력이 생김 |
| 플랫폼 · 앱 인프라 | 현 직무(센티언트 시스템즈), SafeOps의 OTA 배포 · 네이티브 모듈, Plus SMS의 멀티 브랜드 빌드 | 플랫폼 엔지니어로서 맡은 일을 경력 항목에 더 적어야 함 |

## 5. 면접 예상 질문과 답의 실마리

답 전체를 외우기보다, 각 질문에 **꺼낼 사례 하나**를 정해 두세요.

1. **"가장 어려웠던 기술 문제는?"**
   → SafeOps 무음 알림. 채널 → 스트림으로 문제 재정의 → 라이브러리 한계 → Kotlin 모듈 → 채널 id 교체 이유
   → 삼성 예외 → 실기기 3상태 검증. (문제를 다시 정의한 순간을 강조)
2. **"토큰 갱신이 동시에 일어나면?"**
   → 단일 비행 프로미스 + 선제 갱신 + 재시도 표시 + 만료 래치. 아이머그의 4종 토큰으로 확장해서 설명.
3. **"성능을 개선해 본 경험은?"**
   → Plus SMS 가상화. "먼저 쟀다"와 "칩 줄바꿈 때문에 3개씩 묶었다"가 핵심. 측정 방법(무엇으로, 몇 회 평균)을 준비.
4. **"상태 관리는 어떻게 나누나?"**
   → 서버 / 세션 · 전역 모달 / 로컬 세 곳. 파생 상태를 두 곳에서 계산하다 깨진 SafeOps 사례로 마무리.
5. **"낙관적 업데이트의 함정은?"**
   → 되돌림을 idle일 때만 하는 이유(도착 처리한 값이 아직 낙관 캐시값).
6. **"플랫폼 정책 변경에 대응한 경험은?"**
   → targetSdk 36 edge-to-edge. 전제가 무너진 범위를 파악한 방법, SDK 35 경계 상수 공유.
7. **"리드에서 팀원(플랫폼 엔지니어)으로 옮긴 이유는?"**
   → 반드시 나오는 질문입니다. 직함보다 다루는 문제의 층(네이티브 · 배포 · 현장 운영)을 넓히려는 선택이었다는
   식으로, SafeOps에서 실제로 새로 다룬 것(Kotlin 모듈, OTA, 실기기 검증)을 근거로 답을 준비하세요.
8. **"팀 리드로서 한 일은?"**  ← 지금 가장 약한 답변. 보완점 ①을 채우면서 같이 준비하세요.
   (코드 리뷰 기준, 공용 컴포넌트 도입 과정과 반대 의견을 설득한 방법, 30% 측정 방법)
9. **"AI 도구를 어떻게 쓰나?"**
   → 포트폴리오의 AI 안내자(도구 호출 · 주입 방어 · 레이트리밋 · 지연 로딩), 그리고 개발 과정에서
   코드 리뷰 게이트 같은 워크플로우를 운용한 경험.

## 6. 종합 평가 (주관적 점수, 참고용)

| 항목 | 평가 | 한 줄 |
|---|---|---|
| 문제 해결 깊이 | ★★★★★ | 원인이 있는 층까지 내려가고, 근거를 남긴다 |
| 앱/웹 기술 폭 | ★★★★☆ | RN bare · 네이티브 모듈 · 웹 · 3D까지. 백엔드 협업 경험 서술은 적다 |
| 설계 · 구조화 | ★★★★☆ | 판정 일원화, 상태 3분할, 경계 상수 공유 |
| 검증 · 품질 | ★★★★☆ | 실기기 · 실측 · 테스트. 웹 프로젝트의 테스트 서술은 없다 |
| 리더십 증거 | ★★☆☆☆ | 직함은 있지만 이력서 안의 증거가 부족하다 (보완점 ①) |
| 이력서 완성도 | ★★★☆☆ | 프로젝트는 훌륭, 경력 · 기본 정보 빈칸을 채우면 한 단계 오른다 |
